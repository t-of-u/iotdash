เครื่องมือและการ debug

การวัดผลและ debug

วิธีอ่านตัวเลขของบอร์ด, เครื่องมือหา glitch, ความช้า, หน่วยความจำรั่ว, ปัญหา input และฮาร์ดแวร์ พร้อมกรณีศึกษาจริงที่ใช้เครื่องมือเหล่านี้

หลักการ

  • วัดบนบอร์ด สำหรับเรื่องเวลา, glitch และหน่วยความจำ simulator ใช้ตรวจความถูกต้อง (ภาพ, layout, memory safety)
  • ตัววัดต้องตรงกับสิ่งที่ตาเห็น: late เคยเป็น 0 ขณะที่ยังเห็น glitch จึงสร้าง tears ขึ้นมาแทน ก่อนสรุปว่าแก้แล้ว ให้ยืนยันว่าตัววัดจับอาการนั้นได้จริงก่อนแก้
  • ติดป้ายเหตุการณ์: ทุก tear บอก phase ของ engine ทำให้รู้ว่าต้องไปดูส่วนไหน
  • ให้ผู้ใช้ยืนยันด้วยมือจริง: การแตะผ่าน USB ไม่ได้ผ่าน GT911 และไม่เห็นภาพบนจอ

บรรทัด stats

ได้จาก iotdash.py device stats, คำสั่ง text s หรือ log อัตโนมัติทุก 10 วินาที ค่าเกี่ยวกับเฟรมเป็นของเฟรมล่าสุด ค่าตัวนับสะสมตั้งแต่ z

หา glitch ของจอ

  1. z reset ตัวนับ แล้วทำสิ่งที่เห็น glitch (หรือใช้ f วาดเต็มจอ 3 วินาที)
  2. s ดู tears และ phase ที่เกิด:
    • load/io: การอ่าน flash/storage ไม่ถูก pace
    • paint + with blit สูง: blitter แย่ง bus (ดู waitBusWindow, R<MB/s>)
    • idle: ไม่ใช่งานของ engine (driver, DMA priority, interrupt มาช้า)
  3. Tarm แล้วทำซ้ำ จากนั้น T ดู timeline รอบ tear แรก: ระยะห่างระหว่าง fill (ควรใกล้ ~615 µs), VSYNC อยู่ตรงไหน, ตัวไหน busy/TEAR
  4. ทดสอบ bus โดยตรง: F (อ่าน flash 2 วินาที) เทียบ Q (อ่าน PSRAM) ถ้า F ทำให้ dmafb/late ขึ้น แปลว่าการอ่าน flash ใดๆ ระหว่างแสดงผลเป็นปัญหา
  5. ถ่ายภาพหน้าจอแบบ SHOT "s" (page ที่กำลัง scan) เทียบกับภาพปกติ เพื่อแยกว่าภาพใน buffer ผิด (ปัญหา engine, ตรวจด้วย IOTDASH_DAMAGECHECK) หรือภาพถูกแต่ส่งออกจอผิด (ปัญหา scan-out)

หาความช้า

  • ดู stats หลังการกระทำ: ส่วนไหนกินเวลา (style/layout/paint) และ [N el], [full]
  • style สูง + N มาก: selector ที่ทำให้ restyle กว้าง (ใช้ RT_STYLE_DEBUG=1 ใน sim ดู flag sibling/state-on-ancestors)
  • layout [full]: element ที่เปลี่ยนไม่มี relayout boundary (ทำให้ขนาดตายตัว)
  • paint สูง: damage ใหญ่, shadow, transform, รูปขนาดใหญ่
  • P: profile ตาม section บนบอร์ด 3 วินาที (รวม helper busy/engine waited ของการวาดสองคอร์)
  • M: micro-benchmark ของ primitive; m: เปิด/ปิดการวาดสองคอร์เพื่อเทียบ
  • ใน sim: prof … prof, bench, relayout, RT_WANT_DEBUG=1 (ทำไมยังวาดอยู่), spincheck

หน่วยความจำ

  • ดู psram KB (ว่าง) ซ้ำๆ ขณะทำการกระทำเดิมหลายรอบ: ถ้าลดลงเรื่อยๆ คือรั่วหรือ cache ไม่มีขอบเขต
  • js KB โตตามจำนวนหน้า = realm เก่ายังถูกอ้างถึง (APP process)
  • fonts-in-ram โตแล้วไม่ลดหลังเปลี่ยนแอป = สำเนาไม่ถูก collect
  • ASAN build ใน sim สำหรับ use-after-free/overflow
  • คำสั่ง text heap บนบอร์ด: SRAM ภายในที่ว่าง/ต่ำสุด และ stack ที่เหลือของแต่ละ task (ใช้เมื่อ Wi-Fi/Bluetooth เปิดไม่ได้หรือจะเพิ่มสิ่งที่อยู่ใน SRAM)
  • ใน sim: mem [tag] ระหว่างแต่ละหน้าจอใน script, IOTDASH_SLOWMEM=1 ให้ font/รูปถูกคัดลอกแบบบอร์ด, และบน macOS MallocStackLogging=1 + malloc_history PID -allBySize ที่สองจุดเวลา (ใช้ sleep ใน script) แล้วเทียบตาม frame ของ rt:: ว่าใครจองเพิ่ม
  • บอร์ด reset เอง: ดู device log ตั้งแต่ boot (บรรทัดแรกบอก sram/psram ตอนเริ่ม และสาเหตุ reset)

Input

ilog เปิด log ของ input (ดู Touch และ input) แยกได้ว่า: touch มาช้า (sampled … ago), ไปโดน element ไหน, OS รับไปหรือไม่ (-> system), คลิกถูกยกเลิกเพราะอะไร

ฮาร์ดแวร์

  • device probe วัดแรงดันด้วยสายจาก J8 ขา 3 (GPIO6) พร้อมสั่งสาย SD ให้อยู่ในสถานะที่ต้องการ (cs0, sck1, mosiz, …)
  • sd ส่ง CMD0 แบบดิบและอ่าน byte กลับ
  • เทียบกับ firmware ทางการของผู้ผลิต: ถ้าพังเหมือนกัน ปัญหาไม่ใช่โค้ดของเรา

กรณีศึกษา

1. Glitch ทั้งระบบหลังย้ายไป flash

ขั้นสิ่งที่พบ
อาการภาพ/ตัวอักษรเพี้ยนเป็นแถบ, ตอนปัดแถบล่าง, เปลี่ยนหน้า, เริ่มใหม่
ตรวจภาพdamagecheck ใน sim ผ่าน: ภาพใน buffer ถูก ปัญหาอยู่ที่การส่งออกจอ
ทดลองF = 1170 late ใน 2 วินาที, Q = 0 → การอ่าน flash แย่ง bus
แก้รอบแรกfont/รูปเข้า RAM, อ่านไฟล์แบบ pace → late = 0 แต่ผู้ใช้ยังเห็น glitch
บทเรียนlate วัดผิดสิ่ง สร้าง tears (owner bit ของ descriptor) + timeline
สาเหตุที่สองtimeline แสดงการเติมผิด buffer หลัง VSYNC → RESTART_IN_VSYNC ของ driver + priority ของ DMA จอ
ผลtears 0 ทุกสถานการณ์ (เดิม 12–14 ครั้ง/3 วินาทีตอนวาดหนัก)

2. Calculator "กดไม่ติด" หลังเปลี่ยนหน้า

ขั้นสิ่งที่พบ
สมมติฐานแรกcache หรือ navigation ผิด
ilog จากนิ้วจริงทุกการกดถึงแอป (click ครบ) แต่ต่อคิวนาน
stats~130 ms ต่อการกด: style 49–74 ms (59–73 el), layout 24–39 ms [full]
สาเหตุ:active mark subtree ของบรรพบุรุษทุกชั้น + เทียบ custom property ด้วย pointer; flex/grid ไม่มี relayout boundary
ผล~31 ms ต่อการกด (style 4 ms/4 el, layout 2 ms [part])

3. PSRAM ลดลงทุกครั้งที่ใช้แถบล่าง

stats แสดง PSRAM ว่างลด ~100 KB ต่อการเปิดแถบ จนเหลือ 14 KB สาเหตุ: shadow ของปุ่มในแถบที่ fade สร้าง mask ใหม่ทุกค่า alpha และ cache ไม่มีขอบเขต แก้ด้วย LRU 96 KB + quantize alpha ทำให้ต่ำสุดคงที่ ~480 KB

4. ข้อความใน Settings เยื้องขึ้น

ใช้ os ref ให้ Chromium วาดหน้าเดียวกัน แล้วเทียบกับ device shot พบว่าแถว flex ที่มี min-height จัดกลางผิด (~12 px) เป็น bug ของ engine (Flexbox §9.4 ขั้น 8) ไม่ใช่ HTML แก้ที่ engine จึงถูกทุกแอป

5. SD card อ่านไม่ได้

ไล่จากซอฟต์แวร์ไปฮาร์ดแวร์: ตรวจคำสั่ง CH422G เทียบ demo ของผู้ผลิต → อ่านระดับขากลับจากชิป → วัดแรงดันทุกขาในช่องด้วย probe → รัน firmware ทางการซึ่งล้มเหลวเหมือนกัน สรุปว่าหน้าสัมผัสของช่องเสีย (ดู ฮาร์ดแวร์)

6. แอปตาชั่ง ทำ PSRAM หมด

ขั้นสิ่งที่พบ
อาการหน้าแรกของ แอปตาชั่ง เหลือ PSRAM 15 KB แล้วบอร์ด crash
แยกต้นทุนต่อหน้า (บอร์ด)CSS ≈600 KB จาก CSS 34 KB, JS context ≈690 KB, script ≈440 KB, การวาดครั้งแรก ≈450 KB (font ≈290 KB)
หาเจ้าของ (sim)mem ระหว่างหน้าจอ + malloc_history สองจุดเวลา: source ของ function ถูกเก็บซ้ำ, stylesheet ถูก parse ซ้ำทุก <link>, Value ใหญ่, element ที่ถอดยังถือ computed style, font ไม่ถูกปล่อย, และวนจอแล้วโตเรื่อยๆ จาก wrapper ใน cycle ที่ GC ไม่ทำงาน
ตรวจว่าไม่เปลี่ยนภาพเทียบภาพ sim ก่อน/หลังทุกหน้า (ต้องเหมือนทุก pixel) + ASAN
ผลหน้าแรก ≈850–960 KB, ทั้ง flow ≈465 KB คงที่ 20 รอบ (ดู หน่วยความจำ)
