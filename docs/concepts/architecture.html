Runtime 4 layer

หลังเจอ glitch ของจอ (ดู ประวัติ) runtime ถูกจัดเป็น 4 layer ตามความสำคัญ layer บนต้องไม่ถูก layer ล่างทำให้สะดุด:

Layerทำงานที่ไหนหน้าที่สัญญาที่ต้องรักษา
1. ส่งภาพออกจอ (scan-out)hardware LCD + ISR บน core 0 + fill DMAดึงภาพจาก page buffer ใน PSRAM ผ่าน bounce buffer ใน SRAM ไปจอที่ 39 Hz ต่อเนื่องห้ามสะดุดเลย ตัววัดคือ tears = 0 ห้ามมีโค้ดใดอ่าน flash ระหว่างทำงาน และ DMA ตัวอื่นต้องหลบช่วงเติม buffer
2. สร้างเฟรม → pushengine task (core 1) + paint helper (core 0)style, layout, paint ลง back buffer ทีละแถบ แล้ว present() สลับ buffer ที่ขอบเฟรมช้าได้ (เฟรมตก) แต่ไม่ทำให้ layer 1 ภาพแตก วาดผ่าน SRAM band + DMA เท่านั้น
3. Inputtouch task บน core 0 (priority 6)อ่าน GT911 ทุก 8 ms ใส่คิวพร้อมเวลาจริง engine ดึงจากคิวทุกรอบก่อนให้แอปทำงานจับ touch ได้แม้ engine ยุ่ง gesture ของระบบ (แถบล่าง) ทำงานที่ OS ก่อนถึงแอป
4. App processJavaScript บน engine tasktimer, background process, event handler, rAFงบ 10 ms ต่อรอบสำหรับ timer และ process, watchdog ตัดสคริปต์ที่รันเกิน 3 วินาที process หรือ interval ที่ค้างถูกหยุดถาวร

รายละเอียดแต่ละ layer: การแสดงผล, engine, input, JavaScript runtime

หนึ่งรอบของ engine

while (true) {
  devlink.poll();              // PH_IO: คำสั่งจากคอมพิวเตอร์ (screenshot, eval, ติดตั้งไฟล์ ...)
  drainTouch();                // PH_INPUT: event จาก touch task พร้อมเวลาที่ sample
  bool drew = eng->update();   // OS tick, JS (งบ 10 ms), โหลดหน้า, style, layout, paint, present
  if (!drew)                   // ไม่มีอะไรต้องวาด: รอ timer ถัดไป (≤ 16 ms) แต่ touch ปลุกได้ทันที
    xQueuePeek(touchQ, &ev, idleMs);
}

ภายใน Engine::update() ตัวแปร rt::gPhase บอกว่ากำลังทำอะไรอยู่ (load, script, os, layout, paint, io, input, idle) ISR ของจอใช้ค่านี้ติดป้ายให้ tear แต่ละครั้ง ดู การ debug

เส้นทางของการแตะหนึ่งครั้ง

นิ้วแตะ GT911→ touch task (8 ms) + timestamp→ touchQ→ engine: pointerAt()→ OS: gesture แถบล่าง / dialog→ InputController: hit test, :active, click→ JS handler→ DOM เปลี่ยน→ style / layout เฉพาะส่วน→ paint แถบใน SRAM → DMA ลง back buffer→ present() latch ตอนต้นเฟรม→ scan-out

ตัวอย่างต้นทุนที่วัดได้ใน Calculator (หลังปรับแล้ว): style 4 ms (4 element), layout 2 ms (บางส่วน), paint ~25 ms (พื้นที่ ~18,800 px) รวมประมาณ 31 ms ต่อการกด

ข้อตกลงที่ทุกส่วนต้องรักษา

  • CPU ห้ามเขียน page buffer ใน PSRAM ตรง ๆ: ทุกการวาดผ่านแถบใน SRAM แล้วให้ DMA เขียน (DmaBlitter) การเขียนผ่าน cache ทำให้ต้องอ่าน cache line เดิมขึ้นมาก่อน ใช้ bandwidth เป็นสองเท่า
  • ห้ามอ่าน flash ระหว่างวาด: flash กับ PSRAM ใช้บัสเดียวกัน (MSPI) การอ่าน flash ต่อเนื่องทำให้ scan-out เติม buffer ไม่ทัน ภาพของระบบและแอปจึงไม่ถูก map เข้าหน่วยความจำ อ่านผ่าน ImageSource ที่คุมจังหวะเท่านั้น ดู หน่วยความจำและ storage
  • DMA ของจอได้ priority สูงสุดเสมอ: channel ของ LCD = 5, fill DMA = 4, blitter = 0
  • engine และ JS ใช้ thread เดียว (engine task): paint helper อ่านข้อมูลอย่างเดียว ห้าม intern atom หรือแก้ state ที่แชร์ระหว่าง paint
  • ซอร์ส lib/rt ต้อง portable: build ได้ทั้ง ESP32 และ Mac ส่วนที่ต่างกันใช้ hook (Platform, rt::gBulkCopy, rt::gAllocBulk, rt::gIoPause ...)
