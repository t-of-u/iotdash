แกนระบบ (core)

JavaScript runtime

QuickJS ที่ถูกห่อด้วย JsHost (lib/rt/js.h/.cpp): runtime ต่อ app session, context ต่อหน้า, scope ของ timer/process, งบเวลาต่อ tick, watchdog ที่หยุด script ที่ค้าง, event bus ของ OS และ storage นี่คือ layer 4 (app process) ในสถาปัตยกรรม: แอปช้าได้เฉพาะตัวเอง ห้ามลากการแสดงผลหรือ input ไปด้วย

Runtime, context และ realm

ระดับอายุมีอะไร
Runtime (JSRuntime)หนึ่ง app session: สร้างเมื่อหน้าแรกของแอปเปิด, ทำลายใน endSession() เมื่อออกจากแอปheap ของ JS ทั้งหมด, background process แบบ APP, event bus, ไฟล์ที่เปิดอยู่
Context (JSContext, realm)หนึ่งหน้า: สร้างใน reset(doc) และปล่อยใน retirePage() เมื่อเปลี่ยนหน้าglobal ใหม่ทั้งหมด: Web API จาก bootstrap, os.js, script ของหน้า, wrapper ของ DOM node

ทุกหน้าเริ่มต้นสะอาด: ตัวแปร global ของหน้าก่อนไม่ตามมา โค้ดของหน้าก่อนหยุด แต่ realm เก่าจะถูก GC คืนก็ต่อเมื่อไม่มีอะไรอ้างถึงแล้ว ถ้า background process แบบ APP ที่สร้างในหน้าแรกยังถือ closure ไว้ realm ของหน้าแรกจะยังอยู่ (~400 KB ในกรณี Calculator)

stack สูงสุดของ JS 32 KB (เดิม 24 KB: event ที่ซ้อนกัน เช่น keydown → click() → handler → blur() → listener ของ blur ลึกราว 16 frame ผ่าน dispatch ของ bootstrap) task engine จึงมี stack 48 KB ใน SRAM ภายใน ปรับขนาดได้ด้วย environment variable RT_JS_STACK (หน่วย KB) build ที่มี sanitizer มี frame ใหญ่กว่าต้องตั้งเอง เช่น RT_JS_STACK=256

ไม่เก็บ source ของ function

QuickJS ปกติเก็บข้อความ source ของทุก function ไว้ให้ Function.prototype.toString และ function ที่ซ้อนอยู่ข้างในก็อยู่ในสำเนาของ function แม่อีกชั้น script ของหน้าจึงอยู่ในหน่วยความจำสองถึงสามรอบ iotdash ปิดสิ่งนี้ (QJS_KEEP_FUNCTION_SOURCE ค่าเริ่มต้น 0 ใน lib/quickjs/quickjs.c) toString() ของ function จึงได้รูป function name() { [native code] } (ขึ้นบรรทัดใหม่รอบ [native code])

ประหยัด ≈130 KB ต่อการเริ่มหน้า (bootstrap + os.js) และ ≈160 KB สำหรับ script ของ แอปตาชั่ง

ลำดับเมื่อเปิดหน้า

  1. retirePage(): ทิ้ง scope ของหน้าเก่า (timer, rAF, fetch, process PAGE, listener), unpin wrapper ทั้งหมด, JS_FreeContext, JS_RunGC
  2. สร้าง runtime ถ้ายังไม่มี, สร้าง context ใหม่, ใส่ native function ไว้ที่ __n
  3. รัน bootstrap (Web API) ซึ่งเอา __n ออกจาก global ทันที (หน้าเห็นแค่ API สาธารณะ)
  4. รัน os.js (API ของ OS) แล้วรัน script ของหน้า

Scope: APP กับ PAGE

timer, animation frame, fetch, background process และ OS event listener จำ scope ที่สร้างมันไว้ (ไฟล์ที่เปิดค้างไว้ถูกปิดเมื่อจบ session เท่านั้น) สิ่งที่ถูกสร้างจากใน callback จะได้ scope เดียวกับ callback นั้น

Scopeถูกทิ้งเมื่อใช้กับ
PAGE (pageGen_)ออกจากหน้าค่าเริ่มต้นของ setTimeout/setInterval/rAF/fetch และ process ที่ระบุ "PAGE"
APP (kScopeApp = 0)ออกจากแอป (endSession)process ที่ระบุ "APP" และทุกอย่างที่มันสร้าง

Background process

setBackgroundProcess('poll', 'APP', async (info) => {
  const r = await fetch('https://example.com/api');
  …
  return 5000;          // รอบถัดไปอีก 5 วินาที; false = หยุด; ไม่คืนค่า = ใช้ interval
}, 1000);
rmBackgroundProcess('poll');
clearBackgroundProcess('PAGE');   // 'ALL' | 'APP' | 'PAGE'
os.processes();                   // รายการ process
  • รันครั้งแรกทันที แล้วทุก intervalMs (ค่าเริ่มต้น 1000) info = {name, runs}
  • คืน number = delay ครั้งถัดไป, false = หยุด, หรือ promise ของค่าเหล่านั้น (รอบถัดไปนับจากตอน promise settle) process ที่ยังไม่ settle จะไม่ถูกรันซ้อน
  • throw ปกติ: ถูก log แล้วรันรอบถัดไปตาม interval
  • ถูก watchdog หยุด: process นั้นถูกปิดถาวร (log "process X ended: it did not return") เพราะรอบถัดไปจะค้างแบบเดิม
  • ชื่อซ้ำ = แทนที่ตัวเดิม

งบต่อ tick

JsHost::tick() ตั้ง budgetEndUs_ = ตอนนี้ + 10 ms แล้วรัน timer ที่ถึงเวลาตามลำดับ deadline จากนั้น process ระหว่างทางถ้าเกินงบจะหยุด ที่เหลือยังค้างอยู่และรันใน tick ถัดไป ผลคือแอปที่มีงานเยอะทำให้ตัวเองช้า แต่เฟรมยังถูกวาดและ touch ยังถูกส่งทุก tick (งบเป็นการตรวจระหว่าง callback ไม่ได้ตัด callback ที่รันอยู่) timer ที่ถูกเพิ่มระหว่างรันจะรอ tick ถัดไป และรันไม่เกิน 256 ตัวต่อ tick

Watchdog

  • engine ตั้ง deadline ก่อนทุก tick และก่อนส่ง pointer event (armWatchdog(3000))
  • QuickJS เรียก onInterrupt เป็นระยะ ถ้าเลย deadline จะคืน 1 → script ถูกยกเลิกด้วย exception ที่แอป catch ไม่ได้ และ log "app script stopped: it ran for more than 3000 ms without returning"
  • ใช้นาฬิกาจริง (steady_clock) ไม่ใช่นาฬิกาของ platform เพราะใน simulator นาฬิกาเสมือนหยุดเดินขณะ script วน loop
  • setInterval ที่ callback ค้างจะถูก clear ทิ้ง ("setInterval N cleared: its callback did not return")
  • จำนวนครั้งที่หยุดดูได้จาก watchdogStops()

ทดสอบบนบอร์ด: while(true){} ถูกตัดที่ 3.0 วินาที แอปใช้งานต่อได้ จอและ touch ไม่ค้าง

DOM wrapper

JS เห็น DOM node ผ่าน wrapper ที่ถือ reference ของ node ไว้ wrapper ของ node ที่ต่ออยู่ใน document ถูก pin ไว้ ทำให้ property ที่เพิ่มเอง (expando) และ listener อยู่รอด node ที่ถูกถอดออกยังอยู่ตราบที่ JS ถือ wrapper ไว้ event ถูกส่งผ่าน __dispatch เฉพาะชนิดที่มี listener ลงทะเบียนไว้ (listened_) จึงไม่เสียเวลาข้าม JS กับ event ที่ไม่มีใครฟัง

GC หลังเปลี่ยนจอ

แอปที่สร้างจอใหม่ด้วย innerHTML ทิ้ง subtree เดิมทุกครั้ง wrapper ของ node ที่ถูกถอดมักติดอยู่ใน cycle (listener ที่อ้างถึง element ของตัวเอง) ซึ่งมีแต่ GC ที่คืนได้ และระหว่างนั้น node ยังถือข้อมูล layout/paint ที่ QuickJS ไม่ได้นับ GC ของ QuickJS จึงไม่รู้ว่าควรทำงาน (เคยทำให้ PSRAM ลด ≈5 KB ทุกรอบที่วนจอของ แอปตาชั่ง)

JsHost::nodeConnected นับ node ใน subtree ที่ถูกถอดซึ่งมี wrapper อยู่ JsHost::tick เรียก JS_RunGC เมื่อ:

  • นับได้ตั้งแต่ 150 node (ประมาณหนึ่งจอ)
  • ไม่มีการถอด node มา 600 ms แล้ว (หน้านิ่ง ไม่ทำกลาง transition)
  • ห่างจาก GC ครั้งก่อนอย่างน้อย 2 วินาที

GC หนึ่งครั้งใช้ ≈35 ms บนบอร์ด element ที่ถูกถอดยังทิ้ง computed style ทันทีโดยไม่ต้องรอ GC (ดู หน่วยความจำ)

URLอ่านจากหมายเหตุ
relative (เช่น data.json)bundle ของแอป (resolve จาก URL ของหน้า)404 ถ้าไม่มีหรืออยู่ใต้ system/private/; resolve แบบ async เหมือน fetch จริง; อ่านผ่าน ImageSource (paced)

fetch ภายนอกบนบอร์ด

  • task http มี stack 10 KB ใน PSRAM (SRAM ภายในเก็บไว้ให้ radio) ใช้ esp_http_client กับ certificate bundle ของ ESP-IDF สำหรับ HTTPS; buffer ของ TLS อยู่ใน PSRAM
  • ใช้คำสั่งแบบ stream (open → write body → fetch_headers → read) แทน esp_http_client_perform: คำตอบ 4xx/5xx ถึงหน้าพร้อม body ตามปกติ (เดิม 401 ที่ไม่มี auth challenge กลายเป็น error ESP_ERR_NOT_SUPPORTED แอปจึงแยก "รหัสผิด" ไม่ได้)
  • ตาม redirect ไม่เกิน 5 ครั้ง: 301/302/303 ที่ไม่ใช่ GET/HEAD ไปต่อเป็น GET (ไม่มี body และ Content-Type), 307/308 คง method เดิม response.url เป็น URL สุดท้าย
  • body ของคำตอบเก็บไม่เกิน 1 MB และต้องมีที่ใน PSRAM: buffer จองครั้งเดียวจาก Content-Length (ถ้ามี) ต้องมี block ต่อเนื่องพอบวก 64 KB และ PSRAM รวมพอสำหรับ string ของ script อีกเท่าตัว ไม่พอ fetch ล้มด้วย ESP_ERR_NO_MEM (log http: no memory for the answer of URL) แทนที่บอร์ดจะ reset; คำตอบถูก move ไปถึงหน้าโดยไม่ copy (เดิม copy 2 รอบ คำตอบ 174 KB ของ server จริงทำให้ operator new จองไม่ได้และ abort); statusText มีเฉพาะ 200 ("OK"); error ของการเชื่อมต่อได้ชื่อ error ของ ESP-IDF
  • ใน simulator fetch ภายนอกใช้ curl

Script และ module

  • <script src> และ inline script รันตามลำดับในเอกสาร; type="module" ใช้ module loader ที่ resolve path จาก bundle
  • error ที่ไม่ถูก catch ถูกพิมพ์ใน log ของบอร์ด (และ simulator) พร้อม stack
  • console.log ไปที่ log เดียวกัน ดูได้ด้วย iotdash.py device log
