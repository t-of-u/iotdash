Wi-Fi และ Bluetooth

การเชื่อมต่อของบอร์ด: Wi-Fi station, Bluetooth LE แบบ central และการตรวจว่าออกอินเทอร์เน็ตได้จริง OS ถือ policy (เครือข่ายที่บันทึก, การต่ออัตโนมัติ, สิทธิ์ของแอป) ส่วน firmware ถือ radio จริง แอปใช้ผ่าน os.net, os.wifi, os.bt (ดู JavaScript API) และผู้ใช้จัดการได้ที่ Settings → Connection

เครือข่ายที่บันทึกและการต่ออัตโนมัติ

  • เครือข่ายถูกบันทึกลง registry secure.wifi ([{ssid, pass}] ล่าสุดก่อน, สูงสุด 8) เมื่อต่อสำเร็จแล้วเท่านั้น รหัสที่ผิดจึงไม่ถูกจำ
  • wifi.connect ที่ไม่ส่ง pass ใช้รหัสที่บันทึกไว้
  • ตอนระบบเริ่ม (Os::netStart) ถ้า wifi.enabled (ค่าเริ่มต้น true) จะเปิด Wi-Fi, scan แล้วต่อเครือข่ายที่ใช้ล่าสุดที่อยู่ในระยะ
  • ระหว่างที่ไม่ได้ต่อ จะลองแบบเดียวกันทุก 30 วินาที (ยกเว้นมีการต่อที่ค้างอยู่)
  • frame WIFI ทาง USB (iotdash.py device wifi "SSID:PASS") ใช้เส้นทางเดียวกับ Settings: ต่อทันทีและบันทึกเมื่อต่อได้

เครือข่ายที่ติดมากับ system image

ไฟล์ os/core/private/secrets.json (อยู่ใน .gitignore ไม่ถูก commit) ทำให้บอร์ดที่เพิ่ง deploy ต่อ Wi-Fi ได้เองโดยไม่ต้องพิมพ์รหัสบนจอ:

{"wifi": [{"ssid": "Office", "pass": "…"}, {"ssid": "Lab", "pass": "…"}]}
  • os build ใส่ไฟล์นี้ใน system image ที่ system/private/secrets.json ซึ่งหน้าไหนก็อ่านไม่ได้: Engine::open ไม่เปิด และ fetch() ตอบ 404 ทุก path ใต้ system/private/ มีแต่โค้ด native ของ OS ที่อ่าน
  • ตอนระบบเริ่ม OS เทียบ hash ของไฟล์ (FNV-1a) กับ secure.secretsHash ถ้าต่าง จะรวมเครือข่ายในไฟล์เข้า secure.wifi (ตัวแรกในไฟล์ได้ลำดับแรก) แล้วจำ hash ใหม่
  • เครือข่ายที่ผู้ใช้กด Forget จะไม่กลับมาจนกว่าไฟล์จะเปลี่ยน; หลัง Reset registry หรือ factory reset (hash หายไปด้วย) เครือข่ายในไฟล์กลับมาตอนระบบเริ่มครั้งถัดไป
  • รูปแบบเครือข่ายเดียว {"ssid": "…", "pass": "…"} ก็ใช้ได้

รหัสผ่านอยู่ใน os.idb บน storage และใน registry (NVS) แบบไม่เข้ารหัส สิ่งที่กันไว้คือการเข้าถึงจาก script ของแอปเท่านั้น

Bluetooth LE (central)

  • เปิดเมื่อมีคนใช้: Bluetooth กิน SRAM ภายใน จึงไม่เปิดตอน boot คำขอ bt.* แรก (scan, connect, …) จะเปิดให้เองถ้า bt.enabled (ค่าเริ่มต้น true) ถ้าผู้ใช้ปิดไว้จะได้ error Bluetooth is off การปิดคืนหน่วยความจำของ controller และ host task
  • Scan: active scan (ขอ scan response เพื่อให้ได้ชื่อ) นาน ms (ค่าเริ่มต้น 8000, ช่วง 1–60 วินาที) ส่ง event found เมื่อเห็นอุปกรณ์ใหม่หรือเพิ่งได้ชื่อ ผลสุดท้ายเรียงตาม RSSI scan ใหม่ยกเลิกอันเก่า (อันเก่าได้ [])
  • Connect: timeout 10 วินาที, หยุด scan ที่ค้างก่อน (controller scan และ connect พร้อมกันไม่ได้), แลก MTU แล้วค้นทุก service และ characteristic คืน {id, name, type, mtu, services} ต่อพร้อมกันได้ 2 อุปกรณ์
  • จำอุปกรณ์: อุปกรณ์ที่ต่อสำเร็จถูกเก็บใน registry bt.devices ([{id, name, type}] ล่าสุดก่อน, สูงสุด 8) พร้อมชนิด address จึงต่อใหม่ได้โดยไม่ต้อง scan
  • Read / write / notify: ข้อมูลไม่เกิน 512 byte; write แบบรอ response เมื่อ characteristic มี write ไม่งั้นใช้ write without response; subscribe เขียน CCCD (notify หรือ indicate)
  • UUID: 16-bit เป็นตัวเล็ก 4 หลัก ("ffe0"), 128-bit ที่อยู่บน Bluetooth base UUID ถูกย่อเหลือ 4 หลัก, ที่เหลือเป็นรูปเต็ม ค่าที่ส่งเข้าไปไม่สนตัวเล็ก/ใหญ่และรับ 0x นำหน้า
  • id ของอุปกรณ์คือ address เช่น c8:2e:18:a4:01:5d ยังไม่มี pairing/bonding (characteristic ที่บังคับเข้ารหัสใช้ไม่ได้)

SRAM ภายในและ sdkconfig

radio ต้องใช้ SRAM ภายในซึ่งมีน้อย จึงย้ายทุกอย่างที่ย้ายได้ไป PSRAM และลดสิ่งที่ต้องอยู่ใน SRAM:

  • malloc() ทั่วไปเลือก PSRAM ก่อนทุกขนาด (CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=0) ส่วนที่ต้องเป็น internal (WiFi, BLE, stack) ขอด้วย capability ของมันเอง
  • WiFi: TX buffer จองต่อ packet จาก PSRAM แทน static 8 ตัวใน SRAM, RX static 4 ตัว
  • NimBLE host จองจาก PSRAM, central ขนาดเล็ก (2 link), host task stack 4 KB
  • TLS: buffer ของ mbedTLS (~40 KB ต่อ connection) อยู่ใน PSRAM (CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC) ก่อนหน้านี้ HTTPS ล้มด้วย mbedtls_ssl_setup -0x7F00 (หน่วยความจำไม่พอ)
  • stack ของ task http (10 KB) อยู่ใน PSRAM, data cache 32 KB (เดิม 64 KB), bounce buffer ของจอ 12 แถว (เดิม 16), buffer รับของ dev link 6 KB (เดิม 16 KB), task probe สร้างเมื่อใช้ครั้งแรก

ถ้า SRAM ไม่พอ radio จะปฏิเสธพร้อมข้อความ เช่น Bluetooth does not start: not enough memory (25 KB free, 30 KB needed) แทนการเริ่มครึ่งทางแล้วรั่ว (WiFi) หรือ crash ใน stack (NimBLE) ค่า sdkconfig ทั้งหมดอยู่ใน ฮาร์ดแวร์ ตัวเลขจริงดูได้ด้วยคำสั่ง text heap (Dev link)

Settings → Connection

แท็บ Connection ของ Settings (os/core/apps/settings/connection.js) มี segment Wi-Fi / Bluetooth รายละเอียดอยู่ที่ iotdash OS โมเด็ม 4G Cat-1 ถ้าเพิ่มในอนาคตจะอยู่ในแท็บเดียวกัน (ยังไม่ได้ทำ)

Simulator

SimPlatform::radio ส่งต่อให้ FakeRadio ซึ่งตอบช้าเหมือนของจริง (scan Wi-Fi 1.5 วินาที, ต่อสำเร็จ 1.2 วินาที / ล้มเหลว 2.5 วินาที, เปิด BLE 0.3 วินาที, connect BLE 0.7 วินาที) การตรวจอินเทอร์เน็ตใน sim ใช้ curl ของ Mac จึงได้ผลจริง
