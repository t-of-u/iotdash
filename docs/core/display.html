แกนระบบ (core)

การแสดงผล (scan-out)

วิธีที่ภาพจาก PSRAM ถูกส่งไปจอ RGB โดยไม่สะดุด, การวาดเฟรมใหม่แล้ว push เข้าไป, transition แบบ slide ที่ทำใน interrupt, และตัววัด tear ที่ใช้ตัดสินว่าจอ "นิ่ง" จริงหรือไม่ โค้ด: src/rgb_display.h/.cpp, src/dma_blit.h/.cpp, DeviceDisplay ใน src/main.cpp, Engine::render() ใน lib/rt/engine.cpp

หลักการ: scan-out ต้องไม่สะดุด เฟรมใหม่ช้าได้

จอ RGB ไม่มีหน่วยความจำของตัวเอง ESP32-S3 ต้องส่ง pixel ให้ตลอดเวลาตาม clock ของจอ (39 ครั้งต่อวินาที) ถ้าข้อมูลมาไม่ทันแม้ไม่กี่ร้อยไมโครวินาที จะเห็นเป็นแถบภาพเพี้ยน (glitch/tear) หรือทั้งเฟรมเลื่อน ดังนั้นระบบถูกแบ่งเป็น layer ที่มีสัญญาต่างกัน:

Layer 1: Scan-out (kernel)hardware + interrupt บน core 1 ส่งภาพจาก page buffer ไปจอ ห้ามสะดุดเด็ดขาด วัดด้วย tear ซึ่งต้องเป็น 0
Layer 2: Frame create → push (kernel)engine วาดลง back buffer ผ่าน blitter แล้ว present ช้าได้ (เฟรมตก) แต่ห้ามแย่ง bus จาก layer 1
Layer 3: Touchดู Touch และ input
Layer 4: App processดู JavaScript runtime

Bounce buffer และงบเวลา

driver esp_lcd ตั้งเป็น no_fb (ไม่มี frame buffer ของ driver) และ bounce_buffer_size_px = 800 × 12 ทุกครั้งที่ bounce buffer หนึ่งถูกส่งหมด driver เรียก onBounceEmpty() (ISR ใน IRAM บน core 1) ให้เราเติมแถวถัดไป

interrupt ของจอ (และของ DMA ที่เติม bounce buffer) อยู่ core 1 (kLcdIsrCore ใน rgb_display.cpp) เพราะ Wi-Fi และ Bluetooth ทำงานบน core 0 และปิด interrupt ของ core นั้นได้นานหลาย ms: วัดตอนใช้ แอปตาชั่ง ครบ flow ขณะต่อ Wi-Fi และตาชั่ง interrupt บน core 0 มาช้าสุด 6.6 ms (งบ ~615 µs) ได้ late 10 และ tear 25 ครั้ง (จอกระพริบ/ภาพกระโดดชั่วขณะ) ย้ายมา core 1 แล้ว late 0 และ tear 7 ครั้ง ซึ่งเหลือเฉพาะช่วงเปิดหน้า (อ่าน flash)

ISR เติม buffer ด้วย fill DMA (GDMA แบบ memory-to-memory) ไม่ใช่ memcpy ของ CPU: DMA ไม่ผ่าน cache, ไม่บล็อก CPU และใช้ bus สั้นกว่า ถ้าการเติมรอบก่อนยังไม่เสร็จ ISR จะรอได้สูงสุด 250 µs ก่อนถอยไปใช้ CPU copy (นับใน dmafb)

Page buffer, present และ latch

  • back() คือ buffer ที่เก่าที่สุด (จะถูกวาดต่อไป) front() คือเฟรมล่าสุดที่ present แล้ว
  • present() ใส่ back เป็น pending แล้วคืนทันที ISR จะ latch สลับเป็นหน้าที่แสดงเมื่อเริ่มเฟรมถัดไป (pos_px == 0) จึงไม่มี tearing ระหว่างเฟรม
  • waitPresented() รอจน back ไม่ได้อยู่บนจอและไม่ได้รอ latch (มี 2 buffer: ต้องรอการสลับ)
  • เลือก 2 buffer แทน 3 เพราะ PSRAM ต้องเผื่อให้ font ที่ถูกคัดลอกเข้า RAM (ดู หน่วยความจำ) ข้อเสีย: เฟรมที่วาดนานเกินรอบจอเล็กน้อยจะเสียหนึ่งรอบ (~25 ms) เปิด 3 buffer ได้ด้วย build flag -DRGB_PAGES=3 (จะใช้จริงเมื่อ PSRAM ว่างพอ: 750 KB + 1.5 MB)

Damage และประวัติของ buffer

engine วาดเฉพาะส่วนที่เปลี่ยน (damage) แต่ back buffer เก่ากว่าเฟรมปัจจุบัน bufferCount() - 1 เฟรม ดังนั้นทุกเฟรมต้องวาด damage ของเฟรมนี้ รวมกับ damage ของเฟรมก่อนหน้า (damageHistory_, prevDamage_) ไม่เช่นนั้นจะเห็นภาพเก่ากระพริบ

  • สี่เหลี่ยม damage ถูก align แนวนอนทีละ 32 px (DmaBlitter::ALIGN_PX, 64 byte = 1 cache line/burst) clip กับจอ แล้ว merge ตัวที่ซ้อนกัน (เผื่อ 2 px) ถ้าเกิน 12 ชิ้นจะรวมเป็นกรอบเดียว
  • หลัง transition ทุก buffer ถือว่าเก่าทั้งจอ
  • ตรวจความถูกต้องได้ใน simulator ด้วย IOTDASH_DAMAGECHECK=1 ซึ่งเทียบทุกเฟรมกับการวาดใหม่ทั้งจอ (ดู Simulator)

Band blitter และ bus window

ถ้า CPU เขียน PSRAM ตรงๆ cache จะอ่าน cache line ทั้งเส้นจาก PSRAM ก่อน traffic จึงประมาณ 2 เท่าของขนาดภาพ และแย่ง bus กับ scan-out DmaBlitter จึงให้ CPU วาดลง band ใน SRAM แล้วให้ DMA เขียนออกไป PSRAM อย่างเดียว ขณะ DMA คัดลอก band หนึ่ง CPU วาด band ถัดไป

  • ก่อนเริ่มแต่ละ band เรียก RgbDisplay::waitBusWindow(bytes/100 + 20 µs): รอจนการเติม bounce buffer เสร็จและเหลือเวลาพอก่อนการเติมครั้งถัดไป (margin 60 µs) ระหว่าง slide คืนทันที และไม่รอเกิน 2 period
  • จำกัดอัตราเขียนเฉลี่ย 40 MB/s (setMaxRate) เพื่อกระจายงานวาดใหญ่ไม่ให้ระเบิดในช่วงเดียว
  • gBlitActive บอก ISR ว่า blitter กำลังเขียนอยู่ (นับใน tears … with blit)

วาดสองคอร์

DeviceDisplay::render() แบ่งแต่ละ band เป็นซ้าย/ขวา: core 1 (engine) วาดซ้าย task paint1 (core 0, priority 5, stack 9 KB) วาดขวาพร้อมกัน จุดแบ่งปรับตามเวลาที่วัดได้จริงของแต่ละแถบจอ (48 แถบ, เลื่อนครึ่งหนึ่งของความต่าง) ใช้เมื่อ band กว้าง ≥ 128 px และมี ≥ 4096 px การวาดอ่าน document อย่างเดียว (cache ที่สร้างแบบ lazy มี lock ของตัวเอง)

Transition แบบ slide ใน ISR

slide (left/right/up/down, 320 ms) ไม่ได้วาดภาพกลางทางเลย ISR ประกอบแต่ละแถวของ bounce buffer จากหน้าเก่าและหน้าใหม่ที่ offset ต่างกันเอง (ease-out cubic) จึงไม่ต้องเขียน PSRAM เพิ่มและวิ่งได้ 39 Hz เต็ม

  1. engine วาดหน้าใหม่ทั้งหน้าลง back แล้วเรียก transition() → RgbDisplay::slide()
  2. slide() รอ latch ล่าสุด, invalidate cache ของ page (เพราะ DMA เขียน แต่ ISR อ่านด้วย CPU) แล้วตั้ง pending transition
  3. ISR เริ่ม transition ที่ต้นเฟรมที่ latch และเลื่อน offset ทุกเฟรม เมื่อครบจะแสดงหน้าใหม่และปล่อย doneSem_
  4. ระหว่าง slide ไม่ใช้ fill DMA (CPU ประกอบแถว) และไม่นับ tear

Fade (เข้า home ตอน boot) ไม่ใช้กลไกนี้ แต่วาดตามปกติ

ตัววัด tear

Tear = ทุกครั้งที่ panel เริ่มส่ง bounce buffer ที่การเติมยังไม่เสร็จ ตรวจจาก owner bit ของ descriptor ตัวสุดท้ายของการเติมรอบนั้น (gdma_link_get_owner(frxList_[s], fillEnd_[s]) ยังเป็น DMA) ซึ่งตรงกับสิ่งที่ตาเห็นเป็นแถบเพี้ยน เป้าหมายคือ 0 ในทุกสถานการณ์

ตัววัดเดิม late (ISR ใช้เวลานานกว่างบ) ใช้ไม่ได้ เพราะเมื่อใช้ DMA เติม ISR จบเร็วเสมอแม้ข้อมูลจะยังมาไม่ถึง และ late = 0 ทั้งที่ยังเห็น glitch

สาเหตุของ glitch ที่พบและวิธีแก้

1. อ่าน flash ระหว่างวาด

หลังย้ายระบบไปอยู่ใน flash, font, รูป และไฟล์หน้าเว็บถูกอ่านจาก flash ที่ map ไว้ (XIP/mmap) ระหว่างวาด flash กับ PSRAM ใช้ bus เดียวกัน: ทดสอบให้ CPU อ่าน flash ต่อเนื่อง 2 วินาที (คำสั่ง F) จอเติมไม่ทัน 1170 ครั้ง ขณะที่อ่าน PSRAM แบบเดียวกัน (Q) ได้ 0

แก้: เลิก map flash ทั้งหมด อ่านผ่าน ImageSource ทีละ 4 KB + พัก 150 µs, คัดลอก font table และ glyph ที่ใช้จริงเข้า PSRAM, คัดลอกรูปเข้า RAM ตอนโหลด รายละเอียดใน หน่วยความจำ

2. Race ใน driver: RESTART_IN_VSYNC

Arduino เปิด CONFIG_LCD_RGB_RESTART_IN_VSYNC เป็นค่าเริ่มต้น driver จะ restart DMA ของจอทุก VSYNC แต่ไม่ reset ตัวนับ bounce buffer ของตัวเอง ถ้ามี EOF ที่หลงมาหลัง restart จะเติมผิด buffer ทั้งเฟรมเลื่อนไปหนึ่ง bounce buffer (16 แถวในตอนนั้น, ภาพกระโดด) ซ้ำด้วย channel ของจอได้ priority ต่ำกว่า DMA ตัวอื่น ทำให้ปลาย buffer เลย VSYNC บ่อยขึ้น

แก้: ปิดค่านี้ใน platformio.ini (default ของ IDF จะ restart เฉพาะเมื่อเฟรมนั้นเสีย EOF ไป) และตั้ง priority ของ channel LCD เป็นสูงสุด ผล: tear จาก 12–14 ครั้งต่อ 3 วินาทีตอนวาดหนักเหลือ 0

3. Blitter ชนกับการเติม bounce buffer

แก้: waitBusWindow() ก่อนแต่ละ band และ priority 0 ของ blitter

4. การคัดลอก image และการอ่านไฟล์เป็นก้อนใหญ่

การคัดลอก app.idb ลง slot ครั้งละ 64 KB จาก LittleFS เคยทำให้จอกระตุกตอนเปิดแอป แก้: อ่านทีละ 4 KB พัก 150 µs (gIoPause สำหรับ Os::readFile และการอ่านในแอปด้วย)
